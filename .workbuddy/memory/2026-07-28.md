## 修复：「我的电脑·自定义快捷入口」点「浏览」选取文件卡死
- **根因**：`pcicons:pick`（及 `select-directory`、export/import 等）用 `dialog.showOpenDialog(mainWindow, ...)` 弹系统对话框。以 mainWindow 为父窗口时是**模态**的（模态由是否传入 parent 决定，**不是** `modal` 选项），会禁用主窗口交互；但弹窗前未把主窗口置顶，当主窗口被遮挡/最小化恢复/焦点异常时，原生对话框藏到主窗口之后 → 用户既看不到对话框、又因模态点不动主窗口 = 体感「卡死」。
- **修复**：新增 `ensureWindowForeground()`（restore/min/show/focus/moveTop，moveTop 包 try），在 `pcicons:pick`、`select-directory`、`export-exclusion-rules`、`import-exclusion-rules`、`export-scan-txt`、`export-events`、`wsl:export`、`wsl:import`(x2)、`packet-capture:save-download`、`packet-capture:export` 共 11 处 dialog 调用前调用。
- **踩坑**：Electron 31 的类型定义里 `OpenDialogOptions/SaveDialogOptions` 无 `modal` 字段（运行时也不认），最初误加 `modal:true` 被 tsc 报 TS2353；且用脚本删 `modal: true` 行时把 `pcicons:pick` 里同行含 `modal:true` 的 `showOpenDialog` 整行误删，导致 `result` 未赋值（TS2454），已重写该块。
- **验证**：`tsc --noEmit -p tsconfig.json` 通过；`vite build` 主进程产物 `out/main/main.js`(892kB) 与 preload 正常产出，含 12 处 `ensureWindowForeground/moveTop` 引用。renderer 的 `emptyOutDir` 因沙箱 safe-delete 拦截失败（已知环境限制，非代码问题）。

## 性能隐患：`processTracker.resolveProcessName` 同步 execSync
- 该函数用同步 `execSync` 启动 PowerShell 解析进程名（约 300-500ms/次，阻塞主进程事件循环）。实际仅在事件缺失 processName 时兜底（ETW/snapshot 脚本已带 processName），且监控默认关闭，风险低。
- **优化**：加 pid→name 缓存（TTL 5min，上限 2000 条，超限保留最近 1000）。彻底消除极端情况主线程阻塞。

## 第二轮优化：「新增入口→浏览」选取应用仍卡顿
- **根因**：`dialog.showOpenDialog` 未指定 `defaultPath` 时，Windows 会从「上次位置」或「桌面」开始加载；若这些位置包含大量文件、网络/云盘快捷方式，对话框初始化会明显变慢。
- **修复**：`pcicons:pick` 新增 `defaultPath` 参数；前端把当前已填 `target/iconPath` 传给主进程；主进程优先打开其所在目录（不存在则回退到 `home` 或 `ProgramFiles`）。同时加 `performance.now()` 日志 `[pcicons:pick] kind=... duration=...ms`，方便在 DevTools Console 判断卡的是 IPC 还是 Windows 对话框本身。
- **验证**：`tsc --noEmit -p tsconfig.json` 通过；`vite build` 主进程产物含 `defaultPath` 与 perf log。

## TaskManager（系统任务管理器）后台占用诊断（同日第三轮）
- 爸爸反馈 TaskManager 页在后台占用过大。排查结论：**页面打开时主进程被高频 fork PowerShell 拖住，是 AgentSC 后台 CPU 波动的真实来源；关闭页面后前端 clearInterval 会停轮询，主进程不再被唤醒**。
- 元凶（src/renderer/pages/TaskManager.tsx + src/main/taskManager.ts + src/main/hardware.ts）：
  1. `list-processes`（每 3.5s）→ `listProcesses()` 的 `LIST_SCRIPT` 含 `Start-Sleep -Milliseconds 1000` 做 CPU 双采样，每个 powershell 进程存活 ~1.2s；每小时约 1000 次 fork。
  2. `get-live-metrics`（每 2s）→ `getLiveMetrics()` `Promise.all` 并发 2 个 powershell（Win32_Processor / Win32_OperatingSystem CIM 查询）；每小时约 1800 次 fork。
  3. 首次/进程大变动 → `get-file-icons` 一次批量解码所有进程 exe 图标（1 个 powershell，几百图标，2-5s；`extractFileIcons` 已有 500 条 FIFO 缓存，稳态不重复 fork）。
- 结论性数据：页面打开时主进程每秒 spawn ~0.5-1 个 powershell.exe（冷启动 300-500ms + CIM/Get-Process 开销），即 Windows 任务管理器里看到的 AgentSC 后台 CPU 波动。
- 注意区分：若启用「追踪路径/监控」，main.ts 在启动 15s 后常驻 `processTracker` snapshot powershell（每 30s Get-Process 全列）——那是监控功能，非 TaskManager 页，但也会后台常驻。
- 优化方向（待爸爸确认是否落地）：① 去掉 list-processes 的 1s sleep，CPU 采样改由 processTracker 常驻低频快照供给；② get-live-metrics 前端节流到 5-10s + 主进程加 1-2s 结果缓存；③ 轮询与 processTracker 合并，避免重复 fork；④ 图标仅加载可见行。
- **已落地（爸爸确认选「关键两项」）**：`taskManager.ts` `listProcesses` 改为后台 5s 低频刷新 + 读缓存（procRefreshTimer，unref，页面关闭 15s 自停），不再每次 fork 含 Start-Sleep 1s 的 PowerShell 并阻塞 IPC；`hardware.ts` `getLiveMetrics` 加 2s 结果缓存（`liveCache`，避免重复 fork 2 个 CIM powershell）；`TaskManager.tsx` 前端轮询 3500/2000ms → 5000ms。验证：`tsc --noEmit` 通过；`vite build` 主进程产物含 `procRefreshTimer/LIVE_CACHE_TTL`。效果：页面打开时主进程 PowerShell 从「每秒 ~0.8 个」降至「每 5s 共 3 个」且 list-processes 零阻塞；关页 15s 后归零。

## 右键菜单页「未检测到右键菜单项」（同日第七轮，爸爸报 bug）
- **现象**：`pages/ContextMenu.tsx` 打开后表格空，提示"未检测到右键菜单项"。
- **根因**：`src/main/contextMenu.ts` 的 `LIST_SCRIPT`/`setContextMenuEnabled` 全部用 `HKCR:` PSDrive（`Test-Path 'HKCR:\*\shell'`、`Get-ChildItem 'HKCR:\...'`、`Get/Set-ItemProperty -Path 'HKCR:\...'`）。但当前 PowerShell 进程**未挂载 HKCR PSDrive**（Get-PSDrive 仅 HKCU/HKLM），`Registry::HKEY_CLASSES_ROOT\...` provider 在受限进程里 `Get-ChildItem` 也会抛错 → `Test-Path` 全 false → 列表脚本整段 `continue` → 返回空数组。机器实际有 87 个右键菜单项（.NET `Microsoft.Win32.Registry::ClassesRoot` 可正常读到）。
- **修复**：`LIST_SCRIPT` 与 `setContextMenuEnabled` 全部改用 **.NET `Microsoft.Win32.Registry` API**（`OpenSubKey(sub)` / `GetSubKeyNames()` / `GetValue('')` / `SetValue` / `DeleteValue`），完全不碰 PSDrive 与 Registry:: provider。`deleteContextMenu`/`restoreContextMenu` 本就用 `reg.exe`（独立进程，HKCR 合法根，不受 PSDrive 限制）+ `Registry::HKEY_CLASSES_ROOT` 全路径，无需改。
- **验证**：用真实 .NET Registry 脚本实测 → 正确返回 87 项（含 label/command/disabled 解析，如 `123pan`="上传到123云盘"、`disabled:true`）；`tsc --noEmit` 通过。
- **教训**：Windows 沙箱/受限环境里，PowerShell 注册表访问一律走 .NET `Microsoft.Win32.Registry` API，别依赖 `HKCR:` PSDrive 或 `Registry::` provider（前者常缺挂载，后者受限进程抛错）。

## 鼠标键盘模块：全局键盘统计接入（同日第八轮）

## 右键菜单页 label 乱码（同日第九轮）
- **现象**：右键菜单项名显示乱码（如 `◆ ◆ ◆ ToDesk ◆ 芒!◇`、`◆ ◆ ◆ Trea ◆ ◆`）。
- **根因**：**系统性编码错配**。PowerShell 5.1 经管道输出 stdout 默认用系统 ANSI 编码（中文 Windows = GBK/代码页 936），而 AgentSC 所有 `runPowerShell` 用 `execFile(..., {encoding:'utf-8'})` 让 Node 以 UTF-8 解码。GBK 字节被当 UTF-8 解析 → 所有非 ASCII 字符乱码（注册表值本身正常：`ToDeskSendFile`=`使用 ToDesk 快传文件`、`Trae`=`通过 Trae 打开`）。dump Node 收到的字节证实：`ca b9`(GBK`使`)+`ef bf bd`(U+FFFD) 等。
- **修复**：给所有 PowerShell 调用注入 UTF-8 输出前缀：`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8; $OutputEncoding = [System.Text.Encoding]::UTF8; ` + script。涉及 9 个 `runPowerShell` 函数（fileIcons/eventViewer/cert/myComputerIcons/contextMenu/taskManager/hardware/mouseKeyboard/uninstaller）+ `main.ts` 2 处直接 `execFile('powershell',['-NoProfile','-Command',ps])`。`cert.ts`/`myComputerIcons.ts` 之前已用 `-EncodedCommand`(UTF-16LE 脚本) 方式修过、跳过重改。
- **验证**：独立 Node 复现 `execFile('powershell',['-NoProfile','-NonInteractive','-Command', PREFIX+script], {encoding:'utf-8'})` → 解析出 `上传到123云盘`/`上传到夸克网盘`/`使用 ToDesk 快传文件`/`通过 Trae 打开` 全部正确；`tsc --noEmit` 通过(EXIT 0)。

## 网络监控无数据（同日第十轮，爸爸截图"网络安全监控"全 0）
- **现象**：流量/ARP/DHCP 全部显示 0/暂无数据，但页面显示「监控中」。
- **根因**：`src/main/networkMonitor.ts` 的 `scanTraffic/scanArp/scanDhcp` 用 PowerShell 采集，失败时 `catch { return }` 把错误吞掉，前端看不到任何报错；同时 `cleanJson` 对数组 JSON 的边界处理不严谨。
- **修复**：
  1. `ps()` 把 stderr 并入错误信息；`cleanJson` 显式保留 `[...]` / `{...}` 完整边界。
  2. 三个 scan 方法 catch 中记录 `console.error` 并把错误写入 `this.lastError`，`getStatus()` 随状态推给前端。
  3. PowerShell 脚本对可能为单对象/空的集合强制 `@(...)` 数组化。
  4. `NetworkSecurity.tsx` 增加 `lastError` 状态并在顶部显示红色诊断提示；i18n 加 `netsec.error_title`（中文「采集异常」/英文「Collection Error」）。
- **验证**：`tsc --noEmit` 通过(EXIT 0)。
- **后续**：重启应用后若仍无数据，看页面顶部红色提示即可定位是 PowerShell 模块缺失、权限不足还是 JSON 解析失败。

## 渲染丝滑优化（同日第十一轮，爸爸问"怎么让前端不会卡死很丝滑"）
- 派 Explore agent 扫 renderer 性能现状，结论：虚拟化/图标异步/rAF合并/图表关动画/批量IPC 均已落地，热点不在渲染写法。最可疑卡顿源是 `Dashboard.scheduleRefresh` 每次事件批次都 debounce 触发 4 次 IPC 查询；次要隐患 `I18nProvider`/`ThemeProvider` 的 value 字面量未 memo。
- **已落地（4 处）**：
  1. `Dashboard.tsx` `scheduleRefresh` 重构为「基于时间戳的节流（2s 下限保底）+ 最大延迟合并 + 仅页面可见时拉取」。修复原纯 debounce 在持续事件流下因定时器不断重置而永不触发（实时统计卡旧值）；`document.visibilityState!=='visible'` 时跳过，主窗口最小化/隐藏不空转 4 次 IPC。新增 `runRefresh`/`lastRefreshRef`/`REFRESH_INTERVAL=2000`。
  2. `i18n.tsx` `I18nProvider`：`setLocale` 改 `useCallback`；`value` 用 `useMemo(()=>({locale,setLocale,t}),[locale,setLocale,t])` 包裹，消除 Provider 重渲时 40 个消费者级联重渲染。
  3. `theme.tsx` `ThemeProvider`：`setMode/setTheme/toggleTheme/setAccent` 全改 `useCallback`（toggleTheme 依赖 `[theme]`）；`value` 用 `useMemo` 包裹，依赖 7 项稳定引用。
  4. `Uninstaller.tsx`：搜索过滤引入 `useDeferredValue(search)` → `deferredSearch`，`filtered` 的 useMemo 改用 `deferredSearch`；输入框受控即时响应、列表过滤延后到后台提交，避免大列表每次按键同步重算+重渲染掉帧。
- 优先级4（重计算丢 Worker）经核查当前渲染主线程无重计算阻塞热点，无具体落点，不强行改动。
- 验证：`tsc --noEmit` 通过（EXIT 0）；曾因 `theme.tsx` import 漏加 `useCallback` 报 4 错，补 import 后复验通过。

## 左侧菜单滚动卡顿修复（同日第十二轮，爸爸问"为什么滚动左侧菜单会卡顿"）
- **根因（多因素叠加）**：
  1. `Sidebar.tsx` 每个菜单项（30+）挂 `transition-all duration-200`：Chromium 在 `overflow-y-auto` 滚动容器中对带 transition 的子元素，滚动期间会反复做 style recalc / paint，直接拖慢帧率。
  2. 滚动容器 `<nav>` 未提升为 GPU 合成层，内容（渐变背景、半透明边框、阴影）每帧重绘而非由合成线程复合。
  3. `App.tsx` 每秒 `setHeartbeat` + 每 5s `get-watcher-status` 触发 App 整树重渲染，而 `Sidebar` 未 `React.memo`，使 30+ 按钮被周期性协调，打断滚动流畅度。
  4. active 项的绝对定位渐变覆盖层（`absolute inset-0 bg-gradient-to-r`）滚动时需重光栅化/合成。
- **修复（src/renderer/components/Sidebar.tsx，4 处）**：
  1. 菜单项与内层 span 的 `transition-all` → `transition-colors`（仅过渡颜色，避开布局）；顺手把 hover 的 `border` 改为默认 `border border-transparent`，消除 hover 时 1px 边框引起的 reflow。
  2. `<nav>` 加 `transform-gpu`（translate3d 提层），滚动改由 GPU 合成线程处理，避免逐帧重绘。
  3. `Sidebar` 用 `React.memo` 包裹，隔离 heartbeat / watcherStatus 引起的 App 重渲染；其 props（activeTab / onTabChange=setActiveTab / version）引用均稳定，memo 有效；i18n / theme context 变化仍会正常重渲。
- 验证：`tsc --noEmit` 通过（EXIT 0）。
- 注：Electron frameless 窗口在禁用 GPU 加速的机器上本就更易卡，以上为前端可修部分；真实环境需爸爸滚动侧边栏确认流畅度。
